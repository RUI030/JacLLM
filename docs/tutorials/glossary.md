# Glossary

Plain-language definitions of every technical term used in this tutorial. Each entry says what the term means, then why we care. Terms are grouped by topic. Use Ctrl+F to find one.

---

## The basics of LLM training

**LLM (large language model).** A neural network that reads text and predicts the next piece of text. ChatGPT, Claude and Qwen are LLMs. Everything an LLM "knows" is stored in its weights.

**Token.** The unit an LLM reads and writes: a word, part of a word, or a symbol. `walker` might be one token; `visit_neighbors` might be three. All lengths and costs here are counted in tokens. As a rough guide, 1,000 tokens is 700–800 English words or 30–60 lines of code.

**Tokenizer.** The tool that splits text into tokens. Each model family has its own, so the same file can be a different number of tokens for different models.

**Weights / parameters.** The billions of numbers inside the model. "9B" means about 9 billion of them. Training means adjusting these numbers.

**Base model.** A model someone else already trained on huge amounts of general text and code, for example Qwen3.8-27B. We never train from scratch. We start from a base model and teach it Jac.

**Fine-tuning.** Training a base model a bit more on our own data so it gets good at our task.

**Loss.** A single number that says how wrong the model's predictions were on some training text. Training tries to make the loss smaller. **Training loss** is measured on data the model is learning from. **Held-out** (or **validation**) loss is measured on data it never trains on. Only held-out loss tells you whether the model is really learning or just memorizing.

**Gradient.** For every weight, the direction and amount to nudge it to lower the loss. It is computed from the training examples.

**Optimizer step (update).** Actually changing the weights using the gradient. The **optimizer** is the rule for how to change them. We use **AdamW**, which also keeps a running memory of past gradients for every trained weight. That memory (the **optimizer state**) costs a lot of GPU memory.

**Learning rate (LR).** How big each update is. Too big and training is unstable; too small and it learns nothing. Values like `2e-4` mean 0.0002. **Warmup** means starting with a small learning rate for the first few steps. A **scheduler** (for example "linear") lowers it over the run.

**Epoch.** One full pass over the training data. "1 epoch" means the model sees every example once.

**Overfitting.** The model memorizes the training examples instead of learning the general skill. Training loss keeps falling, but it gets worse on new problems. Training too many epochs on the same data is the usual cause.

**Checkpoint.** A saved copy of the model in the middle of training, for example `checkpoint-90` after 90 steps.

## Training stages

**CPT (continued pretraining).** Show the model lots of raw Jac text and train it to predict every next token. It learns what Jac looks like, the way you learn a language by reading a lot of it. See [training_methods.md](training_methods.md).

**SFT (supervised fine-tuning, also called instruction fine-tuning).** Show the model "input → correct answer" pairs and train it to produce the answer. It learns how to respond to a request. See [training_methods.md](training_methods.md).

**Loss mask / loss weight.** In SFT the model reads the whole conversation, but only the answer part is graded. Input tokens have **weight 0** (read, but not learned from); answer tokens have **weight 1** (learned from). **"Seen" tokens** are all of them; **"trained" tokens** are only the weight-1 ones.

**RL (reinforcement learning).** Training by trial and error. The model tries, a grader scores the attempt, and the model is pushed toward attempts that scored well. No correct answer needs to be written down, only a way to score.

**GRPO (Group Relative Policy Optimization).** The RL method we use. For each task the model makes several attempts (a **group**, 8 for us). Each attempt is compared with the group's average: better-than-average attempts are reinforced, worse ones discouraged. See [training_methods.md](training_methods.md).

**Rollout / completion / sample.** One attempt generated by the model during RL or eval.

**Reward.** The score the grader gives an attempt. Ours is the fraction of hidden tests passed, and 0 if the code does not compile.

**Advantage.** How much better or worse one attempt is than the average of its group. It decides how strongly that attempt is reinforced. If every attempt in a group gets the same score, every advantage is 0 and nothing is learned.

**Grader.** The program that scores an attempt. Ours runs `jac check`, then the hidden tests.

**Curriculum.** Ordering training data from easy to hard, like a school syllabus, instead of random order.

## Making training fit on a GPU

**GPU, VRAM, host RAM.** The GPU does the training. **VRAM** is the GPU's own memory: everything being trained must fit in it. **Host RAM** is the computer's normal memory. Our cards:

- **RTX 5080:** 16 GB VRAM, a gaming card.
- **RTX PRO 5000:** 48 GB VRAM.
- **RTX PRO 6000:** 96 GB VRAM, rented online through RunPod.
- **DGX Spark:** a small NVIDIA AI workstation.
- **Apple Silicon Macs:** these share one memory pool between CPU and GPU.

**OOM (out of memory).** The job needed more memory than the GPU has and crashed.

**LoRA (low-rank adaptation).** Instead of changing all billions of weights, freeze them and train a small add-on (an **adapter**) next to each layer. It is like clipping a small correction onto the model instead of rebuilding it. It uses far less memory, and the result is a small file of tens to hundreds of MB.

**Rank (r).** How big the LoRA add-on is. r16 is small, r64 is bigger. Higher rank can learn more but uses more memory.

**Alpha (α).** A scaling knob for how strongly the LoRA add-on affects the model. **rsLoRA** is a variant that scales by α/√r, so changing the rank does not change the effective strength.

**Target modules.** Which parts of each layer get a LoRA add-on. `q, k, v, o` are the attention parts (how tokens look at each other); `gate, up, down` are the feed-forward parts (where most knowledge is stored). We target all of them.

**Quantization, 4-bit, NF4.** Storing each weight with fewer bits to save memory. Normally a weight takes 16 bits; in 4-bit it takes 4, so the model is about 4× smaller. **NF4** is a 4-bit format designed for the way model weights are distributed. It loses a little precision.

**QLoRA.** Quantize the frozen base model to 4-bit, and train a normal LoRA adapter on top. This is how a 27B model trains on a 48 GB card.

**Merge.** Folding the trained adapter back into the base weights to make one standalone model. If you merge into a 4-bit base, the weights are rounded again and accuracy can drop a lot. We keep adapters separate for eval.

**Batch size.** How many examples the model processes at once before one update. Ours is 1, because one long example already fills the GPU.

**Gradient accumulation (grad_acc).** Process several examples one at a time, add up their gradients, and update only once. `grad_acc 10` means 10 examples per update, at the memory cost of 1. It is like asking 10 people for directions and walking the average way, instead of turning at every single answer.

**Packing.** Gluing several short examples into one long sequence so the GPU never processes padding. A "batch of 1" can then hold many short examples.

**Gradient checkpointing.** Save memory by forgetting some intermediate results during the forward pass and recomputing them when they are needed. It is slower but uses less memory. The **`unsloth`** variant also moves data to host RAM ("offload"). That helps on a PC with lots of RAM, but not on our shared server, which has only 32 GB.

**Unsloth, TRL, Transformers, MLX.** Software libraries.

- **Transformers** (Hugging Face) loads models.
- **TRL** provides the trainers for SFT and GRPO.
- **Unsloth** makes training faster and lighter.
- **MLX** is Apple's library for training on Macs.

**Recipe.** A YAML file in `script/train/recipe/` that lists exactly what a run uses: base model, datasets and their order, and every setting. It is the record of what was trained.

## Context length

**Context window / `max_seq_length`.** How many tokens the model can look at in one go. For training, it is the longest sequence we can fit in GPU memory. Longer sequences need more memory.

**Truncation.** Cutting a sequence that is too long, which throws away part of it.

**Chunking.** Splitting a long sequence into separate independent pieces. Each piece loses what came before it.

**Sliding window.** Overlapping pieces, each one keeping the recent history it needs. It works better than chunking, but processes many tokens more than once, so it is slower.

**Hallucination.** The model confidently writes something that is not real, for example importing a file that does not exist or using a wrong path.

## Agents and harnesses

**Agent.** An LLM that works in a loop: it reads the task, calls a tool (read a file, write a file, run the compiler), reads the result, and decides what to do next, until the task is done.

**Tool call.** The model asking the harness to do something, such as "read `main.jac`" or "run `jac check`".

**Harness.** The program around the model that runs this loop. It decides which prompt the model sees, which tools it has, and when it is done. **pi** and **JacHammer/JacBuilder** are existing harnesses. **Jach** is ours.

**Trajectory.** The full record of one agent session: every message, tool call and tool result, in order. One trajectory is one long training example. They often reach 100k–200k+ tokens.

**Compaction.** When a session gets too long for the context window, the harness summarizes or drops old parts to keep going.

**SDLC (software development life cycle).** Building software in phases: understand → plan → scaffold → implement → test → deliver. Jach forces the model through these phases one at a time.

**Scaffold.** The skeleton of an app: files, function signatures and types, with the bodies left empty. **scaffold2impl** is the task of filling in the bodies.

**Gate.** A check the harness runs itself before allowing the next phase, for example "does it compile?" or "do the tests pass?".

**Teacher model.** A strong model (Claude, GPT, GLM and others) used to generate training examples for our smaller model.

**Teacher loop (teacher intervention).** Our model (the **student**) works on a task while a **supervisor** program watches. When the student gets stuck, the teacher (Claude Opus) **takes over** for one step, writes the correct next action, and hands control back. We train the student on those correct actions. We use it instead of GRPO when the student almost never succeeds. See [training_methods.md](training_methods.md#4-teacher-loop-when-grpo-has-no-signal).

**Episode.** One attempt at one task in the teacher loop, possibly with several teacher takeovers inside it.

## Model types

**Dense model.** Every weight is used for every token. A 9B dense model does 9B parameters' worth of work per token.

**MoE (mixture of experts).** The model is split into many **experts** (sub-networks), and a **router** picks a few of them for each token. "30B-A3B" means 30B weights in total but only about 3B **active** for any one token. MoE models are big on disk but cheap to run per token.

**Active (activated) parameters.** The parameters actually used for one token. For a dense model this is all of them; for an MoE, only the chosen experts.

**GGUF, llama.cpp.** **GGUF** is a file format for running models efficiently on local machines, and **llama.cpp** is the program that runs them. We use them to serve the model for eval and agent runs. **Q4_K_M** and **Q8_0** are GGUF quantization levels (about 4-bit and 8-bit).

## Jac and evaluation

**Jac.** The programming language we teach the model. It is a superset of Python with extra features for graphs and full-stack apps.

**OSP (object-spatial programming).** Jac's graph-based style:

- **Nodes** are objects in a graph.
- **Edges** connect nodes.
- **Walkers** move through the graph and act on the nodes they visit.

Ordinary models almost never write this style correctly.

**`jac check` / `jac test`.** The Jac compiler's type check (does it compile?) and its test runner (do the tests pass?).

**Hidden tests.** Tests the model never sees. They are used to grade its code fairly.

**Nitin suite.** Our main evaluation set: 972 Jac problems with hidden tests. Half are **completion** (write a function body) and half are **translation** (convert Python to Jac).

**pass@1.** The percentage of problems solved on the first try. **pass@k** means solved in at least one of k tries.

**McNemar test, p-value.** A statistical test for whether two models really differ on the same set of problems. A **p-value** of 0.29 means a difference this size could easily be luck, so it is not significant. Below 0.05 is the usual threshold for "real".

**Floor / idiomize (data generation).** The **floor** is code from an automatic converter: it works, but it reads like Python. **Idiomize** means an LLM rewrites it into natural Jac. If the rewrite fails the checks, we keep the floor.

**Fence (` ``` `).** The markdown code-block marker. Our `-nofence` datasets have replies as bare code, without the fence.
