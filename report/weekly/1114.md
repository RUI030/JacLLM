# JacLLM progress, 10-24 to 11-14: from training to the real harness

## Summary

- After training, we serve each model to JacBuilder's agent harness (JacHammer / jac_coder on jac 0.34.28). Then we
  check what it builds in a real browser.
- We built 33 test tasks on a ladder from easy to hard. There are 14 one-screen apps, 8 full apps, 6 multi-page
  routing apps and 5 designed UIs. A separate 45-task set feeds the teacher experiment.
- Six models ran the same 13 app and UI tasks. **None of them produced an app whose user flow passes in the
  browser (0 of 13 for every model)**, even though the harness marked 7 to 11 of the 13 as passed.
- The failures are not a total mess. A minimal fix of the 8 broken 1111 apps touched 12% to 30% of the final code:
  8 to 11 small, local mistakes per app. The same mistakes repeat from app to app.
- We set up three parties. The **student** is JacLLM. The **supervisor** is a set of checks that catch loops,
  failed checks and non-Jac style. The **teacher** is Claude Opus, which takes over when the student is stuck.
  This produced 122 episodes with 514 teacher takeovers. From those we built trajectory, mined-fix and
  injected-bug datasets.
- Training on each new dataset moved some partial scores, but not the end result. JacBuilder is a general harness
  built for strong models. A 9B model needs smaller tasks, so we are using JacBuilder to observe and will write our
  own harness.

## 0. Terms used in this report

### How an agent run is put together

From the smallest unit to the largest:

| Term | Definition |
|---|---|
| **Tool call** | One action the model asks the harness to perform, such as writing a file or opening a page, together with the result the harness sends back. |
| **Step** | One reply from the model. It holds optional short reasoning and, in JacHammer, exactly one tool call. One step is one call to the model. |
| **Turn** | Everything between one user message and the agent's final text reply to it: usually many steps. One user message plus many tool calls is one turn. |
| **Session** | One conversation between a user and the agent about one project. It can have several turns, for example "build it", then "add a dark mode". |
| **Run** | One attempt by the model at one test task in the harness, from the request until it stops. Our test tasks have one stage, so a run is one turn. |
| **Episode** | The same thing as a run, but in the teacher experiment (section 5): one attempt at one task, possibly with teacher takeovers inside it. It ends when the supervisor accepts the result or a budget runs out. |
| **Trajectory** | The recorded messages of a run or episode, in order: the request, then every step with its tool call and result. A trajectory is the raw material that training rows are cut from. |

**A tool call:**

```
tool call:   write_code(path="main.jac", content="import from services.todos { list_tasks, add_task } ...")
result:      "Wrote main.jac. Check: OK"
```

**A step** (one model reply):

```
reasoning:   "TodoList calls list_tasks, but main.jac never imports the services module, so the server never loads it."
tool call:   edit_code(path="main.jac", old_string="...", new_string="import from services.todos { ... }")
```

**A turn** (one user message, then many steps, then one reply):

```
user:        "Build a to-do list web app like TodoMVC. One text box at the top: typing a task and pressing Enter adds it ..."
step 1:      list_files(".")                          -> the template's files
step 2:      load_jac_skill("jac-cl-components")      -> the guide's text
step 3:      plan_build(...)                          -> a build plan
...          write_code / edit_code / run_command ... -> check results
step 58:     browser_validate()                       -> PASS
reply:       "The to-do app is ready. Next steps: ..."
```

**An episode.** This is a real one from the teacher experiment, `batch5-class_attendance`. Its folder holds:

| Item | What it is |
|---|---|
| the task | "a class attendance tracker: classes, students, mark present or absent per date, show each student's percentage" |
| `messages_plan.json` | the planning steps; the plan has a module graph, typed signatures and how to verify |
| `messages_build_s0.json`, `_s1.json` | the build steps (122 messages in the first part). A new part starts when the context fills up and is summarized |
| `journal.jsonl` | every step in order, who made it (student, teacher, controller) and the supervisor's verdict on it |
| `teacher/00` to `teacher/05` | 6 takeovers. Each records what the teacher saw, its diagnosis and the step it wrote. One example: "All three attempts kept the untyped REGISTRY ... The fix defines typed obj records ... I ran `jac check` (passed) and `jac test` (1 test passed)" |
| `workspace/` | the final code: `main.jac`, `models.jac`, `services.jac`, `server.jac`, 4 page and component files |
| `summary.json` | `end: success`, 6 interventions, 777 seconds |

### Training data

| Term | Definition and example |
|---|---|
| **Training row** | One training sample: the system prompt, the tool definitions, then a list of messages. Example: a prod-64k row is one real user turn, with as much earlier history from that session as fits in 64k tokens. |
| **Weight** | Each model message in a row has weight 1 or 0. Weight 1 means the model learns to produce that message. Weight 0 means it is only context. Example: in a loop row, the 3 repeated failed edits are weight 0, and the step that breaks out of the loop is weight 1. |
| **SFT** | Supervised fine-tuning: training the model to reproduce the weight-1 messages of the rows. |
| **Adapter (LoRA)** | The small set of trained weights added to the base model. Each model name here (1107, 1110, ...) is one adapter. |
| **prod-64k** | Real sessions from JacHammer's production use (users building their own apps; the agent there was mostly GLM-5.3-Flash), cleaned and cut to fit 64k tokens. It shows the model how the real harness is used. |
| **Reverse development (revdev)** | Take an existing Jac app that is known to work. Write the request a user would have made for it, and have a strong model (Claude) rebuild it from an empty project with the harness tools while we record every step. The original app is never shown to the builder. It is only used to write the request and to check the result. **Why:** inventing tasks gives no known right answer, and real user data has no guarantee that the result works. Starting from a working app gives a realistic task with a checkable answer. Example: a hackathon repo becomes "build an app where ...", and the recorded rebuild becomes a row with planning and build steps. 22 repos gave 97 rows (the dataset used in 1102). |
| **Mined fix** | A row cut from an episode: a file that failed `jac check`, then the later step that fixed it. It teaches a fix the model actually needed. |
| **Injected bug** | A row made by breaking a working file in a way the model was seen to get stuck on, such as a missing import or an unclosed brace. It is kept only if the real tools report the bug, and it ends with the fix. |
| **Minimal fix** | The fewest changed lines that make a broken app pass its user flow. The share of lines changed measures how far the model's app was from working. |

### Evaluation

| Term | Definition |
|---|---|
| **Harness** | The program around the model. It gives the model tools, runs them, returns their results and decides when to stop. Here it is JacBuilder's `jac_coder`, the agent behind JacHammer. |
| **Scenario (task)** | One test request plus the user flow that proves the app works. |
| **Harness verdict** | The harness's own pass or fail at the end of a run (`PASS_SYSTEM_VALIDATED`, `FAILED_ERROR`, ...). |
| **Browser check** | Our check (`e2e_check.py`). It starts the final app, clicks through the scenario's user flow in Chrome and fails on missing text, a blank page, an error overlay or a page error. |
| **Compaction** | When the context fills up, the harness replaces the older history with a summary so the run can continue. |
| **Template splash** | The placeholder page of JacHammer's starting template ("When you start to build, changes will appear here"). Seeing it means the model's code is not mounted. |
| **pass@k** | Out of k runs of the same task, whether at least one passes. |

## 1. Where this fits

```
train (SFT, LoRA on Ornith-9B) -> merge with vision -> Q8_0 GGUF -> llama-server (64k context)
  -> JacBuilder harness (jac_coder agent, 27 tools, jac 0.34.28 sandbox)
  -> harness verdict + our browser check (Playwright runs the task's user flow)
  -> read the trajectory: what went wrong, could the harness or the data fix it
  -> new data -> train again
```

Serving: `script/eval/agent/serve.sh` (one 64k slot, temp 0.6, top_p 0.95, top_k 20). Runs:
`script/eval/agent/run_jaccoder.sh <model> <scenario>`, one at a time, 90 min and 12 GB RAM each. JacBuilder
compacts the context at 0.6 x 65,536 tokens (about 39k).

## 3. How a test task is designed

Each scenario is a folder in `script/eval/agent/scenarios/`:
- `stage_1.md`: the request, written the way a user would ask. It never names the Jac feature the app needs.
- `manifest.json`: harness settings and the template.
- `e2e.json`: the user flow our browser checker runs, for example "add two tasks, reload, both are still there".

The harness's own verdict (`PASS_SYSTEM_VALIDATED`) is not trusted. It passed pages that show Vite's error
overlay or the template's splash screen, so every run is also scored by `e2e_check.py`.

### The ladder, easy to hard

| Level | Set | Tasks | Example request |
|---|---|---|---|
| 1 | `mini_*` | 14 one-screen apps | "Score": a heading, "N points" from 0, an "Add two" button, saved on the server so a reload keeps it. Others: reading list, bill splitter with 2-decimal output, plan tabs, visitor log |
| 2 | `app_*` | 8 full apps modeled on open-source products | to-do list like TodoMVC (Enter adds, checkbox, Delete, "N items left", All/Active/Completed filters in the URL). Also kanban (Trello), bookmarks (linkding), expenses (Actual Budget), recipes (Mealie), poll (Rallly), memos, habits |
| 3 | `routing_*` | 6 multi-page apps | blog with one address per article, a shared nav layout, a members area that sends logged-out visitors to login, search kept in the URL, list/add pages, a "page not found" route |
| 4 | `ui_*` | 5 designed sites | Metrica SaaS dashboard (sidebar, stat cards, searchable table), Ticketly helpdesk (tabs, dialog, thread page), Liftoff gym (schedule filters, class pages), a photographer portfolio, a landing page with pricing toggle, FAQ and waitlist |
| separate | teacher-experiment tasks | 45 (41 train, 4 held out) | paraphrased from open-source GitHub repos, in 8 categories: graph, algorithms, state machine game, permissions, realtime, LLM, non-web, frontend |

## 4. How the reference apps and training data were made (Claude Code)

Claude Code wrote the working apps and the data. The model under test never did.

- **20 designed reference apps** (Ledgerly, Brewline, Harbor, Sprintboard, Pantry, Clientbook, ...). Each one:
  - starts from JacHammer's empty template;
  - is built with `jac install --shadcn` and `jac retheme`, following the jaccoder-design guide;
  - passes `jac check`;
  - passes a full browser flow with no console errors.
  - The second batch of 10 uses file-based routing.
- **Replay through the real harness.** `harness_replay.py` is an OpenAI-compatible server that sends a known-good
  build's tool calls in order. jac_coder runs as usual, so every tool result in a training row is the harness's
  own: check output, plan_build, screenshots, `browser_validate`. Only the model's side is scripted.
- **Synthetic fix sets.** These start from working apps, plant one known problem, and call the real JacHammer
  tools (`jachammer_tools.jac`). The model therefore sees the real `[ACTION REQUIRED]`, `[HINTS]` and LOOP
  DETECTED messages:
  - `router_params` (39 rows)
  - `loop_break` (36 rows)
  - `brace_fix_v2` (40 rows)
- **Minimal fixes of the model's broken apps.** For 1111's 8 broken apps, each was fixed from the model's own code
  with the fewest changes that make the scenario flow pass, one change tested at a time. Files are in
  `output/eval/agent/minfix_1111/`.

## 5. Student, supervisor and teacher

Built as the teacher-intervention experiment (`script/spike/1105 Teacher Intervention/`). It runs in a light
stand-in for JacCoder on jac 0.36.1.

**Student (JacLLM).** It gets JacCoder's prompt and 8 to 9 of its tools. It plans first (a module graph, typed
signatures, a verification section), then builds.

**Supervisor.** This is code, not a model. It decides whether the student is doing something pointless and whether
the result is real:
- A student step counts as a failure on any of these:
  - a tool failure;
  - an identical call repeated on an unchanged workspace;
  - a tool call after the checks already pass;
  - a final answer before they pass;
  - a reply cut off at the token limit.
- A final answer is accepted only when all of these hold:
  - no scratch files are left;
  - every file passes `jac check`;
  - `jac test` passes;
  - every planned module exists;
  - the app uses what its category needs;
  - a web app's frontend mounts (`frontend_check.py`).
- `idiom_check.py` flags non-idiomatic Jac, using `jac check --lint` plus the rules from the Jac skills.
- The supervisor's own findings go only to the teacher. The student sees only what JacCoder would show it.

**Teacher (Claude Opus via `claude -p`).** It takes over after 3 failures at the same place.
- What it sees:
  - the student's visible trajectory so far;
  - a scratch copy of the workspace;
  - `jac check`, `jac test` and `jac run`;
  - the Jac skills;
  - the supervisor's notes.
- What it does:
  - tries its fix in the copy first;
  - writes the student's next step, grounded in what the student can see;
  - the harness then runs that step as if the student had written it.

**Data it produces:**
- Teacher steps that worked: weight 1.
- Student steps: weight 1 only when the whole episode was accepted.
- Mined fixes: a file that failed `jac check`, followed by its later fix.
- Injected bugs: files from accepted episodes broken in the ways the student got stuck, kept only when the tools
  confirm the bug.

**Numbers:**
- 122 episodes (80 archived plus 42 in batch 5), 514 teacher takeovers.
- 76 episodes ended in acceptance.
- Datasets: up to 495 rows in `seg2_mined_injected` and 644 injected-bug rows for batch 4.

**Held-out test without the teacher** (4 unseen tasks x 4 runs):

| | pass@4 | tests pass | planned modules exist | frontend mounts |
|---|---|---|---|---|
| 1105 (before) | 0 | 0% | 12% | 0% |
| 1107 (trained on teacher data) | 0 | 12% | 56% | 0% |

Planning and structure improved. No web frontend ever mounted.

**A lesson about the supervisor.** We then opened the 10 web episodes it had accepted in a real browser. **Only 1
of 10 works.** Its checks were static (tests, `jac check`, compiling the client). The other 9 were trained as
successful trajectories. Since then, every verdict comes from a browser run of the user flow.

## 6. What the model does in the harness, and what goes wrong

The early agent runs (10-26, todo app, jac_coder / opencode / pi) already showed the main pattern. Tool calls are
well-formed and the first errors get fixed. Then the run repeats one or two actions until the budget runs out.

| Behavior | Evidence |
|---|---|
| **Loops** | All 11 failed routing runs of 1107 ended in one. Examples: 25 refused reads of the same file, 364 identical failed `fill`s, `ls` alternated with `ls -la` to slip past the loop detector, a landing page rewritten about 60 times. After a 405, it made 16 curls in a row to `/admin/ops/*` and then wrote a tool call as plain text |
| **Runaway thinking** | 5 of 12 routing runs ended on one 32k-token reply. 4 of 10 1111 runs hit max_tokens |
| **Template never replaced** | It writes components but never replaces `frontend.cl.jac`, so the user sees the template splash: 6/8 apps on 1110, 4/8 on 1111. In the training rows, `frontend.cl.jac` was touched 1 time against 236 writes of `main.jac` |
| **Server module not loaded** | `main.jac` does not import the services in 7 of 8 1111 apps, so every endpoint returns 405. The eighth uses a form that fails to load (`.services`) |
| **React and JS habits instead of Jac** | State without `has`, server calls without `await`, data fetched in the render body, `await` in a non-async function. Node objects are sent to the server, so changes are not saved. Walkers are called like functions |
| **Invented names** | It imports shadcn components it never installed (and hand-writes them), invents icon names (`PlusSignIcon01`) and invents API functions |
| **Wrong Jac version** | Bare JSX with no `return` is 0.36 syntax and rejected on 0.34.28 (2/12 routing runs). Unclosed braces are reported at the end of the file (3/12) |
| **Routing** | Route parameters are never read (4/4 detail pages wrong, no `useParams`). `<a href>` is used instead of `<Link>` |
| **Working against the harness** | It ran `jac start` itself in 7/12 runs, although the platform owns the preview. It reads compiled JS instead of the `.jac` source |
| **Trusting the harness pass** | It stops on the harness's PASS while the page is broken. v1.35 got 11/13 harness passes and 0/13 browser passes |
| **Follow-ups break working code** | Started from a fixed app and asked to polish it: it left JSX unclosed (the server won't start), dropped a `has` fix, and changed the wording |

### Minimal fixes: how far off are the apps?

| App | Mistakes | Working app (lines) | Changed | Share |
|---|---|---|---|---|
| todo | 11 | 115 | 26 | 23% |
| kanban | 9 | 96 | 28 | 29% |
| habits | 8 | 128 | 21 | 16% |
| recipes | 8 | 145 | 18 | 12% |

| poll | 9 | 130 | 35 | 27% |
| bookmarks | 11 | 137 | 33 | 24% |

70% to 88% of the model's code survives the fix. The structure and JSX are usually right. The wiring is wrong:
imports, data flow and the server boundary.

### jac 0.34.28 pitfalls found along the way

These are 13 in all. Some are runtime bugs that `jac check` misses:
- A `def:pub` read is cached and never refreshed after a write, so write-then-refetch shows the old list.
- A server module that only client code imports is never loaded (405).
- `await` in a non-async function passes the check but takes the whole page down.
- A variable named `new` crashes the build.
- An annotated assignment inside a block shadows the outer variable.
- Walkers defined in client files are never registered.

## 10. What we learned about the harness

Using JacBuilder has been an observation step. It is a general harness, written for strong models:
- one long session per app;
- 27 tools;
- a 16k-token system prompt;
- context compacted at 39k.

A 9B model in that setting:
- loses track of what it has done;
- repeats actions;
- uses a large share of its context on the prompt and its own history.

Our goal is our own harness, with tasks cut small enough that a small model can use its context and capacity on
one thing at a time:
- one module or one wiring step per call, each with its own check;
- a fixed file layout (entry, services, components) instead of a template to discover;
- verification that runs the real app in a browser, not a static check;
- the supervisor and teacher kept: the supervisor catches loops and non-Jac style early, the teacher's takeovers
  become training data;
- tool sets per step instead of all 27 at once.
